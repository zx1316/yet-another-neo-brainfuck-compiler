## 简介
这是一个用 C++ 编写的 Brainfuck 优化编译器/解释器。编译产物是 **在 x86 处理器上，64 位 Windows 7 以上系统** 运行的可执行文件。

编译器本身在运行时不需要任何外部编译/链接/汇编工具。

尽管优化能力不强、效率较低，且部分原定优化算法尚未实现，但编译产物在较新 x86 处理器上运行的性能不错。

### 性能测试
| 测试用例          | 编译时间（单次） | Clang 编译时间（单次） | 运行时间（中位数） | Clang 运行时间（中位数） |
|---------------|----------|----------------|-----------|-----------------|
| 6.bf          | 255ms    | \> 600s        | 6.47ms    | 7.24ms          |
| 7.bf          | 262ms    | \> 600s        | 23.9ms    | 26.0ms          |
| 8.bf          | 38.6ms   | 1.09s          | 4.42ms    | 4.72ms          |
| 9.bf          | 90.0ms   | 4.38s          | 4.40ms    | 4.77ms          |
| mandelbrot.bf | 13.3ms   | 858ms          | 212ms     | 380ms           |

说明：
1. 本编译器使用默认优化选项。Clang 的输入为本编译器输出的 C 源文件，优化选项为 `-O3`。
2. 测试平台为：CPU：AMD Ryzen 7 9700X，RAM：DDR5 48G 8000MT/s 双通道。
3. 每个编译产物均运行 9 次。使用 PowerShell 的 `Measure-Command` 测量时间。
4. 6.bf 和 7.bf 直译的 C 代码规模极大，导致 Clang -O3 编译耗时异常。

## 使用方法
### 基本用法
```bash
.\bf-compiler <input_file> -o <output_file>
```

### 高级选项
- `-O0`：关闭优化。
- `-O1`：开启优化。默认开启优化，无须额外添加该选项。
- `--optimize-strict`：启用严格优化（优化时偏保守，不会产生保护空间）。
- `--mem-size <value>`：设置运行时内存大小。单位为字节，范围为 1 到 2147483647，默认 80000000。不包括激进优化产生的保护空间。当优化开启且指针位置全局可确定时，自动忽略该选项。
- `--print-info`：打印优化和代码生成信息。
- `-o <file>`：输出文件到 `<file>`。若不指定该选项，则直接解释执行中间代码。
- `--out-legacy-pe`：使用“遗留”PE 构建方法（**生产环境慎用**，输出的 PE 可能误报毒）。
- `--out-c`：输出 C 源文件而不是 PE 文件。
- `--version`：打印版本信息。
- `--help`：打印帮助信息。

## 构建方法

标准的 Windows 平台 CMake 项目。请使用 3.16 以上版本的 CMake 构建。

无外部依赖。

语言标准为 C++23。编译器需使用 MSVC 或 Clang 的较新版本（已测试 Clang 22.1.3）。需要安装 Windows SDK。

## 代码架构与自我反思

总代码行数：~6300

### 解析器
对应 `parser` 目录。

**功能**：读取 BF 源文件，转化为中间代码或输出 C 源文件。

**赤石/忍俊不禁点**：
1. 表面上是个 class，实际上是个空壳，里面包了两个静态方法。

### 优化器
对应 `optimizer` 目录。

**功能**：将中间代码流图化并进行中间代码优化。

**赤石/忍俊不禁点**：
1. `MidBasicBlock` 是 struct 而不是 class，所有字段裸奔，但当发现设计不合理、需要改动的时候已经不好改了，只能先保持原样。
2. 代码优化算法本身写起来就不可能简洁优雅，一定会赤石，见 `MidBasicBlock` 里的那些优化方法。
3. 以何种顺序调用优化算法也令人难以捉摸，感觉我的优化遍序列写得挺抽象，效率低，见 `CodeOptimizer` 类的 `optimize` 方法。

### 生成器
对应 `generator` 目录。

**功能**：重排中间代码，生成 x86-64 汇编并优化，放置基本块并生成最终的 PE 文件。

**赤石/忍俊不禁点**：
1. 强烈建议不要打开 `x64_basic_block.cpp`，尤其是不要查看 `generateWindows` 方法。
2. 本着代码能跑就不要动的原则，暂时没有对那一坨进行重构。

### 解释器
对应 `interpreter` 目录。

**功能**：直接解释执行中间代码。

**赤石/忍俊不禁点**：
1. 表面上是个 class，实际上是个空壳，里面包了若干静态方法。
2. 解释器要能解释两种基本块。本应实现接口，但实际上没有。因此解释器的方法传入了“虚表”（函数指针结构引用）来获取指令序列/后继。

## 处理流程
### 编译为 C
(BF 源文件) --|解析器|--> (C 源文件)

### 编译为 PE
(BF 源文件) --|解析器|--> (中间代码) --|优化器|--> (优化中间代码) --|生成器|--> (PE 文件)

### 直接解释执行
(BF 源文件) --|解析器|--> (中间代码) --|优化器 + 生成器仅重排|--> (优化中间代码) --|解释器|-->

## 优化细节说明
### 中间代码层面
优化器主要应用这些优化：
- **单基本块循环消除**：识别无副作用指针平衡的单基本块循环，若循环内`测试变量 ±= 奇数`，且`其他变量 = 常量/循环不变量`或`其他变量 ±= 常量/循环不变量`，消除循环并优化为清零、赋值与乘加操作。若没有常数赋值，进一步消除 `if `并在数组两端留出保护空间防止越界。
- **单基本块循环常量外提**：识别指针平衡的单基本块循环，若基本块内存在常数赋值，若基本块内未引用该变量，把这个赋值提到循环前；若基本块内引用该变量，事先展开一次循环，然后把循环内所有引用该变量的地方替换为常数。
- **基本块优化**：基本块内的常量折叠/传播、无效赋值消除、简易公共子表达式、基于预定义规则的化简。
- **基于变量值分析的基本块优化**：全局优化，依赖指针分析、变量值分析。在所有全局指针位置确定的基本块上进行。将变量值分析得到的信息引入基本块优化，并消除指针移动。
- **全局赋值消除**：全局优化，依赖指针分析、活跃变量分析。需要所有基本块的全局指针位置确定。基于活跃变量分析删除无用的赋值。
- **跳转折叠**：对所有仅含一条条件跳转指令的基本块，尽量把条件跳转前提到不含条件跳转的前驱处，若前驱含条件跳转且两者测试条件相同，则修改流图折叠跳转。
- **死代码消除与基本块合并**：通过图遍历删除不可达基本块，绕过空基本块，合并相邻基本块。

实际上，**单基本块循环消除（激进版） + 基本块优化 + 死代码消除与基本块合并**三板斧是最有用的，其他优化的性能提升就没那么明显了。

受限于开发周期，以及考虑到 BF 语言特性，做出以下摆烂决策：
- 无跨基本块的非纸带临时变量（无循环不变量外提、寄存器变量优化）。
- 无全局公共子表达式优化。
- 无全局复制传播优化。
- 无更精确的指针分析（全局指针位置未知但相对某基本块确定，这个是真想做但没精力了）。

### 机器指令层面
生成器主要应用这些优化：
- **简易重排**：把多次使用的内存变量放入临时变量，下移测试用临时变量的产生，上移变量写入，折叠内存变量运算，合并临时变量……在中间代码上进行，为生成 x86 汇编做铺垫。
- **“智能”指令选择**：满足条件时使用 `lea` 代替加减法，使用 `lea`、`add` 和 `shl` 代替乘法，在合适时插入 `movzx` 打破假依赖……
- **条件跳转前运算优化**：将条件跳转前的关于内存/寄存器的一系列满足条件的指令折叠为一条运算指令或比较指令。
- **简易窥孔优化**：用 `mov word ptr, imm` 和 `mov dword ptr, imm` 代替地址连续的 `mov byte ptr, imm`。 用 `inc` 代替 +1，用 `dec` 代替 -1。用 `xor` 代替寄存器 `mov` 清零……

经过反复测试，做出以下反直觉但符合实测数据的决策：
- 循环头未 16 字节对齐。在较新的 x86 处理器上，循环对齐似乎有些玄学/收效甚微。考虑到缓存行、取指块、微操作缓存等一系列复杂因素，主流编译器的默认 16 字节对齐甚至不一定是最优的（网上有相关讨论）。
- 使用
  ```asm
  loop1:
      inc rbx
      cmp byte ptr [rbx], 0
      jne loop1
  ```
  而不是
  ```asm
  loop1:
      cmp [rbx + 1], 0
      lea rbx, [rbx + 1]
      jne loop1
  ```
  前者有依赖但长度更短且有宏融合，后者无依赖。理论上后者更快，clang 默认生成的也是后者，但在自己电脑上实测某些情况下前者略快。

## PE 文件（modern）构建流程说明

1. 编写一段 MASM 汇编（`runtime_modern.asm`），引用 `kernel32` 的 `ExitProcess`，`ucrt` 的 `putchar` 和 `getchar`，并设置 bss 段。
2. 使用 ml64 生成 .exe 文件（`runtime_modern.exe`）。
3. 使用 PE 查看器查看文件信息，记录 PE 头和导入表中的关键字段的偏移量。
4. 将 PE Header、初始化代码、`.rdata` 作为二进制数组（`std::array`）嵌入到编译器中。
5. 在生成 PE 文件时，根据实际指令长度和内存大小修改头信息、段表信息、导入表信息等。
6. 依次写入修改后的 PE Header、修改后的初始化代码、编译生成的机器码、修改后的 `.rdata`。

## 附录：已废弃的 legacy PE 构建方案（仅供参考）
在确定 modern 方案之前，曾尝试过一种 **完全不依赖导入表和重定位** 的 PE 生成方式：

1. 编写一段“自举”C++ 代码（`runtime.cpp`），手动从 PEB 中解析 `kernel32.dll` 并查找 `GetProcAddress`，进而获取 `putchar`/`getchar`/`calloc` 和 `ExitProcess`。
2. 使用 Clang 编译为汇编，手工精调（`runtime.asm`）后交给 MASM（ml64）生成一个极简 PE（仅包含 `.text` 段）。
3. 将该 PE 作为二进制数组嵌入编译器，生成 Brainfuck 程序时修改代码大小、段表信息，并追加真正 BF 指令对应的机器码。

该方案虽然理论上可行且不依赖导入表，但由于生成的 PE 过于“非常规”（无 `.rdata`、无导入表），在 Windows Defender 等安全软件中 **被直接误报为病毒**。考虑到交付可靠性，最终放弃此方案，改用 modern 流程（正常链接 CRT 与 kernel32）。
